# Metadata-first production input retrieval

The six executable sources implement the frozen PRODUCTION_INPUT_DESIGN.md and RAW_PROVENANCE_SCHEMA.json. They perform HTTP retrieval and raw-byte routing only. Numeric CT decoding and pooling belong to the separate production-pooling package; model execution belongs to the separately frozen inference package.

Stage M carries the three verified plane07 metadata contracts and audits each of the other150 TIFFs with prefix/count/IFD requests. Its adaptive count rule is fixed before requests. Classic little- and big-endian TIFFs are handled from each header; inline SHORT values use the first two stored bytes. Every object receives its own validator, byte order and strip layout. All153 contracts must pass before root creates a separate ready pixel plan.

Stage P lists1530 exact multipart requests: five row groups256/256/256/256/128 for each of six contexts on each of51 planes. It requests812,187,648 useful crop bytes and reserves at most1,084,483,584 encoded response bytes. No implicit fill, full-width fallback, retry, URL substitution, coalesced ranges or HTTP200 body is accepted. Payload offsets and hashes retain every original raw multipart body for independent replay.

The parent process persists an exact cap reservation before launching each request child. It runs at most four children, examines all completed children before refilling slots and stops scheduling on failure. Child stdout/stderr use files. Unconditional cleanup drains finished children and terminates remaining process groups, with a bounded TERM-to-KILL interval. Every attempted request receives a PASS or STOP record, including spawn failures and missing/rejected terminal receipts. Failed or unconfirmed requests retain their full reserved charge; partial bytes are separately counted. These counts bound response bodies rather than total wire traffic.

Stage M limits are450 attempts/512KiB encoded bodies/16KiB per response/300seconds; Stage P limits are1530 attempts/1.25GiB bodies/1MiB per response/900seconds. Requests have25-second timeouts and children30-second wall limits. The controller reserves ten seconds for cleanup within each stage deadline. The metadata result records production_started_epoch_seconds; the pixel plan/result preserve that exact epoch. All later plan preparation and review waiting therefore counts toward the shared1500-second M/P/C window. Pooling must enforce the same epoch at start and completion.

Combined M/P run and plan outputs are checked after the final raw-provenance JSON. The reader reserves128MiB for pooling arrays, plans and remaining receipts below the2GiB total production cap. Root/pooling must also check the complete production-acquisition and production-pooling output roots when pooling finishes.
